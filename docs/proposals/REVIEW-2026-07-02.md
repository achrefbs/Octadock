# Review — file-preview + vibe-coding-toolkit proposals

Reviewed 2026-07-02 against that day's codebase (post-fix, 331 tests green at
that time).
Status note 2026-07-03: this is a historical review snapshot. File preview and
STT are now partially implemented, and the current plan lives in `../ROADMAP.md`.
Verdict up front: **both plans fit the architecture well and are buildable as
specced.** The command-verb + service + themed-tool-window pattern they lean on
is real and healthy in the code today. The notes below are the gaps worth
closing before implementation, ordered by how expensive they are to discover
late. Implementation examples for both features live in
[`examples/`](examples/README.md).

## File preview (Quick Look) — sound, with four watch-items

**Architecture fit is genuinely good.** `IFilePreviewProvider` +
`FilePreviewService` mirrors the existing `IOcrProvider`/`OcrService` split;
the card inheriting `ToolWindowBase` gets capture exclusion and theming for
free; `CommandParser`/`CommandDispatcher` already have clean seams for an
`open` verb (see `CommandTokens`).

1. **Protocol-initiated opens are an attack surface.** `octadock://open?filepath=…`
   lets any web page attempt to open an arbitrary local path. Two hardenings:
   require a user confirmation for protocol-initiated previews (not for
   shelf-drop/CLI), and reject UNC paths by default — a `\\attacker\share`
   preview leaks NTLM credentials just by connecting. The existing
   `CommandParser` validation layer is the right place.
2. **Guardrails belong in phase 1, not phase 2.** A synchronous parse of a
   100k-row CSV on open will freeze the card. Stream the first ~500 rows,
   virtualize the grid, and load the rest in the background from day one — the
   proposal says this, but phases it ambiguously.
3. **Focus model diverges from `ToolWindowBase`.** The base class is
   `ShowActivated = false` (correct for overlays). The preview card must take
   focus (Esc to dismiss, type-to-filter), so it needs `ShowActivated = true`
   and click-away via `Deactivated`. Small, but it breaks silently if missed.
4. **Locale pitfalls in the CSV provider.** This machine is es-ES: `;` is the
   default Excel delimiter and `,` the decimal separator. Delimiter detection
   must score candidates per-line (not assume `,`), and numeric-column typing
   should try invariant then current culture. Also open files with
   `FileShare.ReadWrite | FileShare.Delete` so previewing a live log/CSV never
   blocks its writer.

Also: "Explain this file" sends content to a model — keep it opt-in with an
explicit per-file action, given the privacy-first stance in the README.
Suggest adding the text/log provider to phase 1; it is nearly free and high
value for the target audience.

## STT — right engine choice, three realism checks

**Local Whisper via Whisper.net is the right default** and matches the privacy
stance. `ISpeechToTextProvider` mirrors the OCR provider pattern. Checks:

1. **Push-to-talk needs key-release detection the hotkey stack doesn't have.**
   `WM_HOTKEY` fires on key-down only; hold-to-talk requires polling
   `GetAsyncKeyState` or a low-level keyboard hook. Recommendation: ship
   **toggle mode first** (press to start, press to stop — works with the
   existing `HotkeyService` today), add hold-to-talk in phase 2 with a hook.
2. **Paste-at-cursor has sharp edges.** Simulated Ctrl+V clobbers the user's
   clipboard (save/restore around it), and UIPI silently drops synthetic input
   into elevated windows — detect failure and fall back to clipboard mode with
   a notification. The example implementation does both.
3. **Model lifecycle, not model choice, is the UX risk.** `ggml-base` (~142 MB)
   is fine for dictation; the cost is cold-load (seconds). Keep the
   `WhisperFactory` resident after first use and show a "warming up" HUD state
   on the first transcription. Live partials: Whisper is not natively
   streaming — treat partials as experimental (chunked re-decode), or use
   Windows `SpeechRecognizer` for live partials with a Whisper final pass.

Also: microphone access can be blocked by Windows privacy settings for desktop
apps — detect the failure and deep-link `ms-settings:privacy-microphone`.
Handle WASAPI device changes (headset plugged mid-session). Ship CPU-only
first; CUDA/Vulkan runtimes are large native deps.

## Tier list — one reorder, one caution

Agree with Tier 1 as listed. Two notes:

- **Clipboard history** is correctly #1 by value, but it is a privacy feature
  inverted: it must honor the `ExcludeClipboardContentFromMonitorProcessing`
  and `CloudClipboard`/password-manager clipboard formats so it never records
  credentials. Budget that in the M estimate.
- **OCR-to-clipboard (S)** is effectively done after this session's H2 fix —
  the region flow is already gated and hotkey-able; it mostly needs a default
  chord in settings. Cheapest win on the board.

## Suggested order

1. File preview phase 1 (CSV + text/log, shelf-drop + `octadock open`, zoom
   animation with slide-up/spotlight fallbacks).
2. STT phase 1 in toggle mode (Whisper.net, clipboard + paste-at-cursor).
3. OCR hotkey promotion + clipboard history.
4. Preview phase 2 (stats/export/pin), STT hold-to-talk + dictionary.
