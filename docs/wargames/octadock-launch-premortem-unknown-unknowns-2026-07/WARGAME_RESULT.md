## Executive Verdict

- **Overall launch readiness:** Not launch-ready — the entire commerce layer is a paper spec bolted onto a privacy utility that contradicts it. Every locked money-path decision (trial gate, license service, signing, installer, website, email, admin panel) is 100% greenfield (`Octadock.sln` holds 5 client projects, zero server code), while the app is `0.2.0-alpha` shipped as an unsigned framework-dependent zip.
- **Biggest hidden risk:** The download's own feature set — global keyboard hook (`DictationGestureMonitor.cs`), clipboard listener (`ClipboardMonitor.cs`), HKCU Run key (`StartupRegistration.cs:16`), screen capture, and a 640MB remote fetch (`ParakeetModelStore.cs:23`) — is a textbook infostealer fingerprint on an unsigned binary, so SmartScreen/EDR quietly eat the funnel and the local-only trial means the founder sees downloads but cannot see why nobody buys (R1). It is on no P0 list.
- **Biggest false assumption:** That swapping the ratified Paddle-merchant-of-record decision for standard Stripe was cost-free — it silently re-accepted EU/UK VAT liability owed from sale #1, with no OSS/UK registration and Stripe Tax disabled (R5, `PAYMENT_PROVIDER_DECISION.md:11,164`).
- **Biggest operational gap:** There is no front door — no website, host, DNS, CDN download-count source, or transactional email (`ADMIN_PANEL_SPEC.md:450` still lists the email provider as a blocking open question), and no launch-day alerting or reconciliation poll, so the solo founder cannot distinguish "SmartScreen is eating my funnel" from "nobody came" (R9, R4, R3, R29).
- **Biggest trust/privacy gap:** "Nothing leaves your PC unless you send it" is falsified on day one — pressing Dictate triggers an unconsented 640MB HuggingFace download under a "fully offline" tooltip (`DockPill.cs:393`), and "Explain Region Aloud" pipes up to 120,000 chars of captured text to cloud CLIs while toasting "Summarizing with local AI" (R6, R7).
- **Biggest implementation sequencing correction:** Stop building the admin panel as a role-based enterprise console for a team of one — rescope it to one live launch-health page and sequence the money-path safety nets (signing, installer, Stripe-signature verification, reconciliation, email, trial gate) ahead of it (R28); gate the trial at the ~8 singleton service seams, never the 13-16 scattered UI call sites (R16).
- **Top 5 changes before paid beta:**
  1. Sign every release via Azure Artifact Signing under one stable identity, ship a self-contained single-file installer (no .NET runtime prerequisite, runs without admin), and warm SmartScreen reputation with weeks of free-build traffic before checkout opens (R1, R10, R14).
  2. Build the license-service money-path correctly: verify Stripe-Signature before any issuance, ship an hourly Stripe-to-license-DB reconciliation poller, consume `charge.refunded`/`charge.dispute.created` to revoke, and pass a twice-run live-mode $49 end-to-end rehearsal (R3, R12, R21).
  3. Decide one tax posture (confirm Managed Payments eligibility, revert to Paddle, or enable Stripe Tax + OSS/UK — else restrict Checkout to US/CA) and publish the legal set (privacy policy, EULA, refund policy, EU immediate-supply consent checkbox) before the first live charge (R5, R19, R22, R23).
  4. Make manual key entry the primary documented activation path (Settings paste box + inline key on the success page), and build the trial gate as a focusable, UIA-announced window with visible refusals at hotkey/Explorer/protocol entry points (R2, R16, R18).
  5. Rewrite the promise to capture-scoped truth ("Your captures never leave your PC"), add a one-time model-download consent card where Cancel actually cancels, relabel the "local AI" explainer, publish a network-egress table, and store the entitlement as an Ed25519-signed file outside the self-wiping `octadock.db` (R6, R7, R11).

### P0 Alerts
Delivered to founder email + phone push, not just rendered on a dashboard (R29). The first four are launch gates; enable Stripe's native webhook-failure email on day one as the zero-code interim layer.

1. **Webhook failure/staleness** — any failed `checkout.session.completed` delivery, or >60 min since last successful delivery (Stripe Webhooks page + license-service oldest-unprocessed-event age >15 min) (R3, R29).
2. **Reconciliation diff >0** — hourly Stripe-API poll of paid Checkout sessions minus licenses issued; any nonzero value persisting >60 min pages (R3). This is independent of webhook receipts by design — signature-verification failures never enter an internal queue.
3. **License email delivery** — delivered rate <98% over the trailing 50 sends, any spam complaint, or bounce spike on the email provider dashboard (R4).
4. **Activation success rate <90%** over the last 20 attempts, broken down by failure reason; a `signature failure` spike within 24h of a license-service deploy means old verifiers are rejecting new entitlements (R2, R13, R15).
5. **Unknown-key activation** — any activation attempt referencing a key the service never issued; threshold 1. This is the only forged-license/keygen canary that works under fail-open entitlements (R12, R20).
6. **Refund/dispute** — any Stripe dispute (threshold 1 while sales <200, R22) and a non-empty "refund without revocation" exception list (R21).

### P0 Admin Actions
Every action below writes an immutable audit row before it commits (spec P0 acceptance :379-381).

1. **Resend license key** — delivered only to the exact Stripe customer email on file, uniform response wording, rate-limited 3/day/email and per-IP (R39).
2. **Deactivate device / migrate slot** — the only recovery for "new laptop, device limit reached" until self-serve ships (R13).
3. **Revoke license** — auto-triggered by `charge.refunded` / `charge.dispute.created` consumers, with manual override (R21).
4. **Reinstate license** — the mirror action for mistaken refunds/revocations.
5. **Issue replacement key / courtesy license** — also the sanctioned fix for "trial expired early," since the trial is local and support cannot extend it remotely (spec :452, R36).
6. **Link Stripe object ↔ license / resolve reconciliation exception** (R3).
7. **Change owner email / merge purchases** — requires step-up proof (Stripe receipt or card last-4); logs before/after addresses (R4, R35, R39).
8. **Erase PII** — deletes email and device names, retains salted key hash + Stripe tax records under legal obligation, writes an immutable audit row (R19).
9. **Extend update entitlement** — cheap goodwill lever for launch-window complaints (R14).
10. **Add support note.**

### P0 Audit-Log Events
Append-only table; no UI required at P0 (R28).

1. Admin login success/failure (with source IP/ASN).
2. License record viewed (PII access).
3. License key resent (destination address recorded).
4. Device deactivated / slot migrated.
5. License revoked / reinstated / replacement key issued.
6. Refund or dispute processed → resulting entitlement change.
7. Owner email changed (before/after values).
8. Update entitlement extended.
9. PII erased (immutable; records what was retained and why).
10. Support note added/edited.
11. Any export or bulk read of customer data.

Verbatim from ADMIN_PANEL_SPEC.md "Never Collect" (:58-68). No launch metric, chart, or debugging convenience overrides this list, and the "Windows version distribution from activation metadata" tile (:242) must be constrained to the published egress table so it never grows into it (R6):

## Final Recommendation

**Is the plan ready to execute?** No — not as currently written, though it is close to ready once reconciled. The locked decisions describe a coherent commercial model, but they silently dropped a ratified P0 tail (cloud-send consent, Credential Manager hygiene, legal set, reconciliation poll, self-serve deactivation, a11y/design minimums), inherited Paddle-era assumptions that don't survive the Stripe swap (tax posture, Customer Portal as the account surface, dunning/refund flows), and sequence the admin panel — the least revenue-critical component — ahead of the things that make the app sellable at all: signing, installer, license service, gate, website, and policies. The codebase side is unambiguous: every commercial component is 100% greenfield, and several existing behaviors (silent protocol failures, self-wiping DB, unscoped privacy copy, "local AI" labeling) actively contradict the plan's happy paths.

**What should happen before implementation begins?** Three things, in order. First, today: start the long-lead clocks — Artifact Signing identity validation, Stripe MP eligibility check, DNS/mail subdomain provisioning. These cost hours and buy weeks. Second, the founder decision batch above, recorded in one dated page that supersedes the conflicting docs (especially the post-expiry verb matrix, tax posture, device definition, and updates clock) — without it, the gate, schema, and checkout copy each get built twice. Third, the doc debt: retire octadock-build-plan.md's M3/M4, amend the PRD's Non-Goals and Beta-3 phasing, and right-size ADMIN_PANEL_SPEC's P0 to the minimal panel — otherwise the next engineering agent to read the repo will build to stale instructions.

**What should Fable/Codex inspect next?** Five targeted checks, all cheap: (1) whether the migration runner refuses a database with `user_version` greater than it knows — the UI wargame's still-open blocking question; (2) whether `TrySalvageAsync` restores the settings table after corruption rebuild (bears directly on where trial state can live); (3) a Stripe test-mode experiment: one-time purchase → open a Customer Portal session and observe what a zero-subscription customer sees (R30's whole design leans on this unverified capability); (4) Windows.Media.Ocr on clean unpackaged Win10 2004 and Win11 VMs (R24 — a paid headline feature with an ADR claiming it needs package identity the zip doesn't have); (5) the "Windows 10/11" support claim against the actual test matrix before it appears in the trust strip.

**What should be deliberately left unknown until beta data arrives?** Price elasticity ($49 vs $59 — ship $49, watch conversion and refund reasons); the 7-day-extension take-rate and day-of-purchase distribution (tunes trial visibility, not mechanics); Pro pricing and metering design (waitlist volume and BYO-key usage patterns should shape it — building metering now would be speculative); trial length 14-vs-21 days; whether the beta plans page shows the Pro column at all; and the final Context scope (beta users' export/copy behavior is the best available signal for what a "context packet" should actually contain). None of these block launch, and deciding them now would substitute guesses for the only data the beta exists to produce.
